## Critical Failure Matrix

| Failure point | Can the event be lost? | Can it duplicate? | Data impact | Recovery mechanism |
|---|---:|---:|---|---|
| DB commit / outbox write | **No.** Same transaction: both or neither | No | None: state and event are atomic | n/a |
| Outbox → Kafka (relay) | **No.** The row stays until the broker acks | **Yes.** Crash after ack, before mark | None (consumers dedupe) | Relay retry each poll; inbox |
| Kafka → consumer | **No.** The offset is committed only after success; retention 7 days | **Yes.** Redelivery after a crash or rebalance | None | Inbox; natural keys |
| Consumer → PostgreSQL | **No.** Rollback leads to redelivery or retry | Yes (blocked by the inbox or unique keys) | None | Retry topics → DLT → replay / saga recovery |
| Consumer → MongoDB (Fraud) | **No.** The offset is committed after persist + publish | Yes (the decision is re-published) | None: one assessment per payment, decision stable | Retry → DLT → saga recovery re-issue |
| Saga step (reply handling) | **No.** Inbox + saga + outbox in one transaction | Yes (stale/duplicate replies) | None: step guards | Recovery scanner re-issues the step's command |
| Compensation step (release) | **No.** Outbox-published command; release idempotent | Yes | None: release is a no-op on RELEASED/REJECTED; tombstone if early | Recovery re-issue, then MANUAL_REVIEW after budget |
| Settlement rail call | Outcome can be **unknown** (timeout) | Yes (re-submission) | Rail deduplicates by idempotency key = paymentId; one settlement row | Resume on redelivery / recovery; MANUAL_REVIEW, never auto-release |
